# Модуль provenance: происхождение файлов

## 1. Задача

По потоку событий SIEM ответить на вопросы: *как файл появился в событии*, *что с ним делали
раньше*, *куда он ушёл*. Построчная обработка событий на это не способна — нужен граф,
сохраняемый между событиями.

## 2. Модель графа

**Узлы** (`ProvenanceNode`): `file`, `process`, `user`, `endpoint`, `url`.
Идентификатор узла — `kind:нормализованный_ключ` (пути нормализуются: разделители и регистр).

**Рёбра** (`ProvenanceEdge`): `src → dst`, действие, время, событие, узел, пользователь, процесс,
атрибуты. Действия: `read`, `write`, `create`, `copy`, `move`, `rename`, `archive`, `encrypt`,
`decrypt`, `upload`, `send`, `delete`, `execute`.

Правила построения графа по событию (`provenance/builder.py`):

| Ситуация в событии | Что добавляется в граф |
|---|---|
| Событие с процессом/пользователем и файлами | рёбра «субъект → файл» с действием файла |
| Есть и процесс, и пользователь | ребро «пользователь → процесс» (запуск процесса) |
| Есть внешний адрес/URL | рёбра «файл → адрес» с направлением наружу |
| Разные действия файлов (`sourceFilename` = read, `targetFilename` = create/copy) | ребро «файл-источник → файл-результат» (копирование/перемещение) |

Сетевой адрес становится узлом только если он относится к получателю данных: адрес агента
(`agent.ip`), локальные и приватные адреса внешними не считаются.

## 3. Хранилища

| Backend | Когда применять | Особенности |
|---|---|---|
| `memory` | тесты, разовая обработка | данные теряются при остановке |
| `sqlite` | одна реплика сервиса (по умолчанию) | WAL, переживает перезапуск, индексы по `src`/`dst`/`ts` |
| `redis` | несколько реплик (общий граф) | точка расширения: описан контракт `ProvenanceStore` |

Схема SQLite: таблицы `nodes` (id, kind, key, label, first_seen, last_seen, attributes)
и `edges` (id, ts, src, dst, action, event_id, host, user, process, attributes).

Очистка: `prune(ttl_seconds)` удаляет рёбра старше TTL и «осиротевшие» узлы.
По умолчанию TTL — 7 суток (настраивается `provenance.ttl_seconds`).

## 4. Восстановление цепочки

```
ProvenanceBuilder.chain_for(path, event=None, as_of=None)
  │
  ├─ стартовый узел: file:<нормализованный путь>
  ├─ обход в ширину по инцидентным рёбрам, глубина ≤ provenance.max_chain_depth (16)
  ├─ фильтр по окну: времени события (или as_of / текущего момента) минус TTL
  ├─ сортировка шагов по времени, устранение дублей (event_id + действие + объекты)
  └─ если рёбер нет и передано событие — синтетический шаг «первое наблюдение объекта»
```

Каждый шаг получает направление и связанный объект:

| Поле шага | Смысл |
|---|---|
| `direction` | `self` (действие субъекта), `inbound` (получено), `outbound` (передано) |
| `counterpart_path` | второй файл в операции (источник копии или её результат) |
| `endpoint` | внешний адрес, если шаг связан с передачей данных |
| `actor_user`, `actor_process`, `host`, `event_id` | субъект и контекст действия |

**Важно про TTL:** при обработке исторических событий окно отсчитывается от времени события,
поэтому в вызове передаётся само событие (или `as_of`). Запрос «сейчас» для данных старше TTL
даст пустую цепочку — это ожидаемое поведение (в реальном развёртывании журнал живёт в окне TTL).

## 5. Влияние на обогащение и риск

* в документ добавляются `provenance_chain` (плоский список шагов), `provenance_chains`
  (по объектам), `provenance_depth`, `external_destinations(_count)`;
* глубина цепочки и внешние адреса учитываются риск-скорингом: повторное обращение к файлу,
  который ранее отправляли во внешний адрес, получает более высокий риск
  (это проверяется в сквозном сценарии, проверка №18);
* правила политик используют `provenance_depth` и `external_destinations_count`
  (правила POL-008, POL-001, POL-003).

## 6. Ограничения

| Ограничение | Причина | Что делать |
|---|---|---|
| Узел «узел сети» (`host`) не выделен в граф | для демонстрационного сценария хватает атрибута на рёбрах | повысить до узла для анализа lateral movement |
| Нет связи с содержимым файла (хэш есть не всегда) | у SIEM-событий редко есть хэши обеих версий | использовать `sha256` из события, когда он присутствует |
| Граф на SQLite не разделяется между репликами | файловая БД на под | включить backend `redis` при масштабировании |
| Цепочки ограничены TTL | не хранить метаданные бессрочно | увеличить TTL или выгружать цепочки в SIEM |
| Копирование внутри события восстанавливается только при наличии источника | в событии может быть только целевой файл | правило «источник → результат» сработает, когда источник присутствует |
