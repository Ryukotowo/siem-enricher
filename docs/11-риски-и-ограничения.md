# Риски и ограничения

Документ фиксирует ограничения программного средства и риски проекта с указанием способов
их снижения. Материал полезен для главы «Оценка» ВКР и для честного позиционирования работы.

## 1. Ограничения программного средства

| № | Ограничение | Причина | Влияние | Что можно сделать |
|---|---|---|---|---|
| О1 | Классификация не анализирует содержимое файлов | в событии SIEM содержимого нет; доступ к данным создал бы новый канал утечки | неверный класс при «обманчивом» имени (`отчет.xlsx`, внутри — персональные данные) | подключить модуль анализа содержимого как отдельный источник признаков |
| О2 | Модель обучена на именах файлов (не на путях) | так сформирован датасет НИР | на нетипичных именах точность падает (измерено: 0.463 по классам) | гибридные правила (уже реализовано, 0.772) + дообучение на своём датасете |
| О3 | Класс `secret` моделью не предсказывается | в модели нет такой категории | криптоматериалы определяются только правилами по имени/расширению/каталогу | расширить датасет категорией `secret` и переобучить |
| О4 | Маскирование не затрагивает поля, не перечисленные в правиле | правило перечисляет конкретные пути | в `raw_event` могут остаться исходные пути других полей | перечислять все «путевые» поля источника либо не публиковать `raw_event` |
| О5 | Хранилище provenance на SQLite не разделяется между репликами | файловая БД на под | при нескольких репликах цепочки неполные | включить backend `redis` (контракт `ProvenanceStore` готов) |
| О6 | Окно provenance ограничено TTL (7 суток) | не хранить метаданные бессрочно | цепочки по «старым» файлам пусты | увеличить TTL или выгружать цепочки в SIEM |
| О7 | Блокировка зависит от внешней системы | сервис не управляет правами | без SOAR/EDR/Active Response реальной блокировки нет | реализовать исполнителя под конкретную EDR (интерфейс `BlockExecutor` готов) |
| О8 | Требуется `torch` (~250 МБ) для ML-режима | трансформер | вес образа и требования к ОЗУ | `--build-arg INSTALL_ML=0`, режим `heuristic`, либо квантизация/ONNX |
| О9 | Задержка ~148 мс/событие на CPU | инференс mBERT | ограничение пропускной способности (~7 соб/с на процесс) | батчинг, GPU, вынос инференса в отдельный сервис, фильтрация событий по `min_rule_level` |
| О10 | Сопоставление полей SIEM задаётся таблицей псевдонимов | схемы источников различаются | для экзотических схем потребуется расширение `FIELD_ALIASES` | добавить псевдонимы в конфигурацию (`extractor.aliases`) без правки кода |
| О11 | HTTP-слой и Kafka-коннекторы не покрыты автотестами в этом окружении | недоступна установка пакетов | риск регрессий при доработке | тесты на стенде с установленными fastapi/aiokafka (команды в docs/08–09) |
| О12 | Метрики качества модели частично получены на обучающих данных | для честной оценки нужно переобучение | возможна переоценка качества | использовать стратифицированное деление в `train_transformer.py` и указывать условия измерения |

## 2. Риски проекта

| Риск | Вероятность | Влияние | Снижение |
|---|---|---|---|
| Модель из НИР обучена на синтетическом датасете, слабо отражает реальные имена | средняя | ложные классы на реальных данных | гибридные правила; сбор датасета из реальных событий; дообучение |
| Ложные срабатывания раздражают аналитиков | средняя | снижение доверия к системе | режим `dry_run`, настройка порогов, тег вместо алерта для низкого риска |
| Ложная блокировка парализует работу пользователя | низкая | простой | `dry_run` по умолчанию, запрет `live` в `dev`, `stop_on_block`, журнал аудита |
| Рост нагрузки на инфраструктуру из-за обогащения | средняя | задержка обработки событий | метрики длительности, батчинг, горизонтальное масштабирование, фильтр по уровню правила |
| Утечка данных через сам обогатитель | низкая | компрометация данных | сервис не читает содержимое; маскирование; непривилегированный контейнер; read-only ФС; NetworkPolicy |
| Расхождение версий модели и интерпретации результатов | низкая | неверные выводы | версия модели в каждом событии (`sensitivity_model_version`), версия схемы в `enrichment.schema_version` |
| Изменение формата событий источника | средняя | потеря метаданных | псевдонимы полей в конфигурации; предупреждение при отсутствии файлов в событии |
| Сроки: доработка под требования кафедры | средняя | задержка защиты | документация и метрики готовы; текст ВКР вне проекта |

## 3. Что осознанно не реализовано

| Возможность | Почему | Где точка расширения |
|---|---|---|
| Анализ содержимого документов | новый канал доступа к защищаемым данным, отдельная большая задача | источник признаков для классификатора |
| Карантин файла | требует интеграции с EDR/антивирусом | `QuarantineExecutor` (действие возвращает `skipped` с пояснением) |
| Инференс как отдельный микросервис | избыточно для одного процесса; усложняет стенд | `ml.type` + HTTP-клиент как классификатор |
| Redis-хранилище provenance | нужно только при нескольких репликах | `ProvenanceStore` (описан контракт, `build_store` возвращает понятную ошибку) |
| UI/дашборд | вне рамок ПС; метрики отдаются в Prometheus, журнал — в SIEM | Grafana на стенде (`--profile observability`) |
| Аутентификация HTTP API | сервис разворачивается внутри периметра, доступ ограничен NetworkPolicy | middleware FastAPI / mTLS на уровне ingress |

## 4. Направления развития

1. **Качество модели**: дообучение на реальных именах, аугментация (транслит, опечатки, годы),
   добавление класса `secret`, метрика «доля пропущенных конфиденциальных объектов».
2. **Больше контекста в признаках**: обучение на строке «имя + каталог» (`ml.text_template`
   уже поддерживает), учёт типа процесса и получателя.
3. **Производительность**: ONNX/квантизация, GPU, кэш результатов классификации по имени файла
   (имена повторяются, кэш даст кратное ускорение), батчирование по топику.
4. **Интеграции**: исполнители блокировки под конкретные EDR/SOAR, обратная запись вердиктов
   в SIEM, автопереобучение по подтверждённым инцидентам.
5. **Эксплуатация**: готовые дашборды Grafana, алерты на деградацию ML (`ml_fallback_total`),
   нагрузочное тестирование (locust), chaos-тесты недоступности Kafka.
