# Архитектура сервиса обогащения событий SIEM

## 1. Компоненты

| № | Модуль | Код | Ответственность |
|---|---|---|---|
| 1 | Коннектор к SIEM | `connectors/` | подписка на поток событий, подтверждение обработки, checkpoint |
| 2 | Извлекатель метаданных | `extractor/` | приведение «сырого» события к канонической модели, извлечение файлов, процессов, пользователей, адресов |
| 3 | ML-классификатор | `ml/` | класс конфиденциальности по имени файла + правила по размещению и пометкам |
| 4 | Модуль provenance | `provenance/` | граф происхождения, хранение, восстановление цепочек |
| 5 | Обогатитель | `enricher/` | сборка результата, риск-скоринг, формирование документа для SIEM |
| 6 | Модуль политик | `policy/` | проверка условий, выполнение действий, журнал аудита |
| 7 | Обратный коннектор | `connectors/` | возврат обогащённых событий в SIEM |
| — | Сервисный слой | `service/` | HTTP API, метрики, среда выполнения конвейера |
| — | CLI | `cli.py` | запуск, отладка, проверка конфигурации |

## 2. Поток обработки одного события

```
 Kafka (siem.raw.events)
     │
     ▼
 1. KafkaSource.stream()            исходное событие (JSON)
     │
     ▼
 2. MetadataExtractor.normalize()   NormalizedEvent: файлы, процесс, пользователь, адрес, правило
     │
     ▼
 3. HybridSensitivityClassifier     SensitivityAssessment: класс + уверенность + обоснование
     │  ├─ TransformerSensitivityClassifier (имя файла -> категория -> класс)
     │  └─ HeuristicSensitivityClassifier  (каталог, гриф, расширение -> класс)
     ▼
 4. ProvenanceBuilder.record()      узлы и рёбра графа -> ProvenanceStore (SQLite/Redis)
    ProvenanceBuilder.chains_for()  ProvenanceChain: шаги read/copy/archive/upload + внешние адреса
     │
     ▼
 5. RiskScorer.score()              RiskAssessment: 0..1, уровень, компоненты, объяснение
     │
     ▼
 6. EnrichedEvent.to_siem_document() плоский документ с полями обогащения
    PolicyEngine.evaluate()          три фазы: условия -> действия -> решения
     │
     ▼
 7. MultiSink
    ├─ KafkaSink      -> siem.enriched.events
    ├─ FileJsonlSink  -> var/enriched_events.jsonl
    └─ WebhookSink    -> REST SIEM/SOAR (или заглушка mock-siem)
```

## 3. Обоснование ключевых решений

### 3.1 Почему отдельный сервис, а не плагин SIEM

Плагин привязан к внутренностям конкретной SIEM и её версии. Сервис общается с SIEM через
поток событий (Kafka) и HTTP, поэтому одинаково работает с любой платформой, масштабируется
независимо и может быть отключён без остановки SIEM (события просто идут без обогащения).

### 3.2 Почему Kafka как основной канал

* события уже проходят через шину или легко в неё попадают (Filebeat/Logstash-коннекторы);
* сервис не создаёт нагрузку на хранилище SIEM запросами;
* сохраняется порядок событий по ключу, есть буферизация при пиках (важно для ML-инференса);
* подтверждение обработки (commit) выполняется только после успешной отправки результата —
  событие не теряется при падении сервиса.

Файловый реплей (`file_replay`) используется как режим воспроизводимой демонстрации и в тестах;
Elasticsearch и Wazuh Indexer оставлены как необязательные примеры коннекторов.

### 3.3 Почему классификация по имени файла

* имя файла присутствует в событии и не требует вскрытия документа;
* анализ содержимого означал бы доступ сервиса к самим защищаемым данным и новый канал утечки;
* имена файлов в организациях шаблонны (`Зарплатная_ведомость_2025.xlsx`), что делает задачу
  обучаемой (в НИР получено 1600 размеченных примеров, 6 категорий).

Ограничения компенсируются гибридной схемой (см. 3.4) и модулем provenance.

### 3.4 Гибридная схема классификации

| Источник признака | Что учитывает | Приоритет |
|---|---|---|
| ML-модель (mBERT) | смысл имени файла | базовая оценка |
| Правила содержания (паспорт, зарплата, договор) | явные маркеры в имени | повышают класс, если модель неуверена |
| **Правила размещения** (каталог `keys/`, `HR/`, `Public/`) и грифы | организационное решение о классе | **приоритет над моделью** |

Обоснование приоритета: размещение файла в общедоступном каталоге или явный гриф — это
решение организации, а не гипотеза о содержании. Модель может «уверенно ошибаться» на именах
вне обучающего распределения (пример: `Шаблон_письма_клиенту.docx` — модель относит к
коммерческой тайне из-за слова «клиент», правила — к открытым данным по каталогу `Public`).

Ограничение: слабые признаки размещения (`Projects/` → internal) класс **не понижают**:
секреты могут оказаться в любом каталоге.

### 3.5 Модель происхождения

Событие разбирается в граф: узлы — файл, процесс, пользователь, сетевой адрес; рёбра —
действия (`read`, `copy`, `archive`, `upload`, `send`, `encrypt`, `rename`). Для файла
цепочка восстанавливается обходом в ширину с ограничением глубины (`max_chain_depth`)
и окна времени (`ttl_seconds`).

Такое представление позволяет отвечать на вопросы, недоступные при построчной обработке:
«кто отправил файл, который ранее скопировали на съёмный носитель», «обращались ли к файлу
после его отправки во внешний адрес». Именно поэтому внешние адреса из цепочки учитываются
в риск-скоринге последующих событий.

### 3.6 Три фазы применения политик

1. **Проверка условий** на исходном документе (пока ничего не изменено);
2. **Выполнение действий**, причём маскирование — последним, чтобы не разрушать поля,
   по которым проверяются другие правила;
3. **Фиксация решений**: метрики, журнал аудита, итоговое решение (максимум по критичности).

Решения по правилам принимаются до действий — это исключает ситуацию, когда правило низкого
приоритета не срабатывает из-за того, что правило высокого приоритета замаскировало путь.

### 3.7 Блокировка: dry-run по умолчанию

Блокировка — единственное действие, меняющее состояние инфраструктуры. Она выполняется только
при `policy.mode = live` и наличии исполнителя: webhook (SOAR/EDR) или Wazuh Active Response.
Во всех остальных случаях действие фиксируется как `simulated` с пояснением в журнале аудита.

## 4. Отказоустойчивость

| Сбой | Поведение |
|---|---|
| Модель не загружена / нет torch | переход на правила, метрика `ml_fallback_total`, предупреждение в логе |
| Ошибка классификации одного объекта | событие обогащается с классом по умолчанию, предупреждение в `enrichment.warnings` |
| Ошибка построения цепочки | событие обогащается без цепочки, предупреждение фиксируется |
| Недоступен приёмник | событие не подтверждается (offset не коммитится) — будет обработано повторно |
| Некорректное событие в потоке | пропускается со счётчиком ошибок источника, конвейер продолжает работу |
| Ошибка условия правила | правило считается невыполненным, фиксируется предупреждение |

## 5. Масштабирование

* сервис без состояния: несколько реплик читают один топик в одной consumer-группе;
* цепочки происхождения требуют общего хранилища — при нескольких репликах используется
  сетевой backend (Redis); SQLite подходит для одной реплики;
* инференс батчится (`ml.batch_size`) и выполняется на CPU; при необходимости включается CUDA
  (`ml.device`), либо модель выносится в отдельный сервис инференса (точка расширения);
* в Kubernetes предусмотрены HPA по CPU и `startupProbe` (загрузка модели занимает время).

## 6. Безопасность сервиса

* контейнер работает от непривилегированного пользователя, в K8s — read-only корневая ФС,
  сброшенные capabilities, NetworkPolicy;
* сервис не читает содержимое файлов и не имеет доступа к файловым ресурсам пользователей;
* маскирование чувствительных полей выполняется по правилам (`mask_field`);
* журнал аудита содержит решения, но не содержит замаскированных значений в открытом виде;
* секреты (пароли Kafka, токены) передаются через переменные окружения и Secret K8s.
