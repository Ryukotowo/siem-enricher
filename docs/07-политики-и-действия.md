# Применение политик: правила, действия, аудит

## 1. Назначение

Модуль политик превращает результат обогащения в **действия**: маскирование чувствительных
полей, алертинг, теги для корреляции и блокировку (через внешние системы). Правила
декларативны и хранятся в `config/policies.json`, поэтому их можно менять без правки кода
и перезагружать на работающем сервисе (`POST /v1/policies/reload`).

## 2. Структура правила

```json
{
  "id": "POL-001",
  "title": "Отправка конфиденциального файла во внешний адрес",
  "description": "Свободное описание для аналитика",
  "enabled": true,
  "priority": 100,
  "severity": "critical",
  "tags": ["exfiltration", "data-leak"],
  "when": {"all": [
    {"field": "data_sensitivity", "op": "gte", "value": "confidential"},
    {"field": "action", "op": "in", "value": ["upload", "send"]},
    {"field": "external_destinations_count", "op": "gte", "value": 1}
  ]},
  "then": [
    {"type": "alert", "channel": "siem", "severity": "critical", "message": "Возможная утечка"},
    {"type": "mask_field", "fields": ["files[*].path", "user.name"], "strategy": "hash"},
    {"type": "tag", "value": "dlp:exfiltration"}
  ]
}
```

* `priority` — порядок проверки (по убыванию);
* `severity` — критичность правила (для отчётности);
* `decision` не задаётся: он выводится из набора действий
  (`block` > `mask_field` > `alert`/`notify` > `tag` > `allow`).

## 3. Условия

Группы: `all` (И), `any` (ИЛИ), `not` (НЕ), вложенность любая.

Поля — пути по обогащённому документу, включая списки: `files[*].path`, `data_sensitivity`,
`risk_score`, `sensitivity_confidence`, `files_count`, `external_destinations_count`,
`provenance_depth`, `user.is_privileged`, `raw_event.data.win.eventdata.targetFilename`.

| Оператор | Смысл |
|---|---|
| `eq`, `ne` | равенство (для строк — без учёта регистра) |
| `in`, `not_in` | значение входит в список |
| `gte`, `gt`, `lte`, `lt` | сравнение: числа, классы конфиденциальности (по рангу), уровни критичности, даты |
| `contains`, `not_contains` | подстрока (без учёта регистра) |
| `regex`, `not_regex` | регулярное выражение |
| `exists`, `missing` | наличие/отсутствие поля |
| `len_gte`, `len_lte` | длина значения (например, число файлов в списке) |

Семантика: условие выполнено, если **существует** хотя бы одно значение поля, удовлетворяющее
оператору (для `not_*` — если таких значений нет).

## 4. Действия

| Тип | Параметры | Что делает |
|---|---|---|
| `mask_field` | `fields`, `strategy` (`hash`/`tokenize`/`redact`/`partial`) | заменяет значения полей |
| `alert` | `channel`, `severity`, `message`, `webhook_url` | запись в журнал аудита + опциональный вебхук |
| `notify` | `message`, `severity`, `webhook_url` | уведомление внешней системы (требует вебхук) |
| `tag` | `value` | добавляет тег события (корреляция в SIEM) |
| `block` | `target` (`process`/`file`/`user`/`host`/`ip`), `mode`, `reason` | блокировка через исполнителя |
| `quarantine` | `target` | карантин файла — точка расширения под EDR |

Стратегии маскирования:

| Стратегия | Пример `C:\HR\Ведомость.xlsx` | Когда применять |
|---|---|---|
| `hash` (по умолчанию) | `sha256:8cfd9497ba3d0a70` | сохранить сопоставимость, не раскрывая значение |
| `tokenize` | `tok_5f0b1f2c…` (HMAC, секрет `POLICY_TOKEN_SECRET`) | стабильные псевдонимы между запусками |
| `redact` | `***` | полное скрытие |
| `partial` | `C:\***xlsx` | оставить узнаваемость для аналитика |

## 5. Порядок применения: три фазы

```
Фаза 1. Проверка условий на исходном документе (ничего не изменено)
        └─ при срабатывании правила с block и stop_on_block=true правила ниже не проверяются
Фаза 2. Выполнение действий; маскирование — последним
        └─ поэтому правило низкого приоритета, опирающееся на путь файла, всё равно сработает
Фаза 3. Фиксация: итоговое решение (максимум по критичности), метрики, журнал аудита
```

Отложенное маскирование — важная деталь: без неё правило POL-006 (копирование на съёмный
носитель, проверяет `files[*].path` по регулярному выражению) не срабатывало бы после
маскирования путей правилом POL-001 (проверка есть в `tests/unit/test_policy_engine.py`).

## 6. Режимы работы

| Режим | Что происходит |
|---|---|
| `dry_run` (по умолчанию) | маскирование, алерты и теги выполняются; блокировка фиксируется как `simulated` |
| `live` | блокировка передаётся исполнителю: webhook (SOAR/EDR) или Wazuh Active Response |

Исполнители блокировок (`policy/blockers.py`):

| Исполнитель | Условие выбора | Поведение |
|---|---|---|
| `DryRunBlocker` | `mode != live` или нет исполнителя | запись решения, сообщение «не выполнялась» |
| `WebhookBlocker` | `mode=live` + `POLICY_WEBHOOK_URL` | `POST {target, reason, event_id, risk_score}` |
| `WazuhActiveResponseBlocker` | `mode=live` + `WAZUH_API_URL` | `PUT /active-response` (IP/host; для process/file — «не поддерживается») |

Режим `live` запрещён в окружении `dev` (проверка конфигурации возвращает ошибку) — это защита
от случайного включения реальных блокировок на стенде разработки.

## 7. Базовый набор правил (9 правил)

| ID | Приоритет | Уровень | Условие (кратко) | Действия |
|---|---|---|---|---|
| POL-001 | 100 | critical | конфиденциальный файл + отправка + внешний адрес | алерт + маскирование пути/пользователя + тег |
| POL-002 | 95 | critical | класс `secret` с уверенностью ≥ 0.5 | алерт + блокировка (dry-run) + тег |
| POL-003 | 80 | high | конфиденциальные данные + ≥ 10 файлов в событии | алерт + тег |
| POL-004 | 75 | high | архивирование/шифрование конфиденциальных данных + риск ≥ 0.5 | алерт + тег |
| POL-005 | 60 | medium | конфиденциальные данные + непривилегированный пользователь + кадровый/финансовый каталог | алерт + тег |
| POL-006 | 70 | high | копирование данных на съёмный носитель | алерт + тег |
| POL-007 | 90 | critical | шифрование/переименование в крипто-расширение | алерт + блокировка (dry-run) + тег |
| POL-008 | 50 | medium | глубина цепочки ≥ 4 + внешний адрес в цепочке | алерт |
| POL-009 | 10 | low | открытые данные + риск < 0.3 | тег (контрольный «белый» пример) |

Проверка срабатывания — `tools/smoke_pipeline.py` (каждое правило проверяется на своём сценарии)
и `tests/integration/test_pipeline_end_to_end.py`.

## 8. Журнал аудита

`var/logs/policy_audit.jsonl` — по одной записи JSON Lines на решение и на действие:

```json
{"kind": "policy_decision", "rule_id": "POL-001", "decision": "mask", "severity": "critical",
 "priority": 100, "mode": "dry_run", "event_id": "1700000000.000006",
 "data_sensitivity": "confidential", "risk_score": 0.83,
 "reasons": ["data_sensitivity gte 'confidential'", "action in ['upload', 'send']"],
 "actions": [{"type": "alert", "status": "executed"}, {"type": "mask_field", "status": "executed"}],
 "audit_ts": "2025-03-03T09:41:02Z"}
```

Журнал пригоден для: разбора инцидентов, отчёта о срабатываниях, доказательной базы
для ВКР (сколько правил и в каких режимах сработало). Доступ через API: `GET /v1/audit?limit=50`.

## 9. Ограничение маскирования (важно)

Маскирование изменяет только те поля, которые перечислены в правиле. Поле `raw_event`
содержит исходное событие целиком, поэтому:

* в POL-001 перечислены конкретные «путевые» поля `raw_event` (targetFilename, sourceFilename,
  destinationUrl) — они маскируются;
* если в исходном событии есть другие поля с путями, они останутся открытыми.

Варианты для боевого внедрения: перечислять все «путевые» поля источника в правиле либо
не публиковать `raw_event` в приёмник (точка расширения: параметр «не передавать исходное
событие» для правил с маскированием). Ограничение зафиксировано в
[11-риски-и-ограничения.md](11-риски-и-ограничения.md).

## 10. Как добавить правило

1. Добавить объект в `config/policies.json` (уникальный `id`);
2. Проверить: `python -m siem_enricher validate-config --config config/config.local.json`;
   валидатор сообщит о неизвестных операторах, пустых условиях и действиях без параметров;
3. Прогнать сценарий: `python tools/smoke_pipeline.py --config config/config.local.json`;
4. На работающем сервисе: `POST /v1/policies/reload` (без перезапуска).
