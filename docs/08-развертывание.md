# Развёртывание и эксплуатация

## 1. Требования

| Компонент | Минимум | Рекомендуется |
|---|---|---|
| Python | 3.11 | 3.12+ |
| CPU | 2 ядра | 4 ядра (ML-инференс на CPU) |
| ОЗУ | 1 ГБ (без ML) | 2–3 ГБ (mBERT в памяти ~1.2 ГБ) |
| Диск | 200 МБ (код) + 700 МБ (веса модели) | + место под `var/` (журнал, SQLite) |
| Внешние сервисы | Kafka (или файл событий для демонстрации) | Kafka + Redis (несколько реплик) |
| Доп. зависимости | — | `torch` + `transformers` (ML), `aiokafka` (Kafka), `fastapi`/`uvicorn` (HTTP) |

Ядро работает на стандартной библиотеке: без ML и Kafka сервис запускается на файловом
реплее — это режим демонстрации и тестов.

## 2. Установка

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1

pip install -e ".[service,kafka,config,http]"   # сервис без ML
pip install -r requirements-ml.txt              # + torch (CPU) и transformers
pip install -e ".[all,dev]"                     # всё сразу

python -m siem_enricher validate-config --config config/config.local.json
python tools\smoke_pipeline.py --config config/config.local.json
```

## 3. Профили конфигурации

| Файл | Назначение | Источник | Приёмник | Provenance |
|---|---|---|---|---|
| `config/config.local.json` | локальная демонстрация | `file_replay` | файл JSONL | `memory` |
| `config/config.example.json` | боевой профиль | `kafka` | `kafka` | `sqlite` |
| `config/config.docker.json` | стенд Docker | `kafka` | `multi`: Kafka + файл + webhook | `sqlite`/`redis` |

Подстановка переменных окружения: `${VAR}` и `${VAR:-значение-по-умолчанию}` (см. `.env.example`).

## 4. Запуск

```powershell
# 1. Демонстрация без инфраструктуры
python tools\generate_sample_events.py --scenario mixed --count 120 --out var\generated.jsonl
python -m siem_enricher replay --config config\config.local.json `
    --input var\generated.jsonl --output var\enriched_events.jsonl

# 2. HTTP-сервис (обогащение по запросу + метрики)
python -m siem_enricher serve --config config\config.local.json --port 8080
#    GET  /healthz, /readyz, /metrics, /v1/version, /v1/policies
#    POST /v1/enrich, /v1/enrich/batch, /v1/classify, /v1/provenance/chain

# 3. Конвейер целиком (Kafka -> обогащение -> Kafka)
python -m siem_enricher run --config config\config.example.json

# 4. Отдельные операции
python -m siem_enricher classify --config config\config.local.json --path "C:\keys\id_rsa"
python -m siem_enricher chain --config config\config.local.json --path "C:\HR\Ведомость_2025.xlsx"
python -m siem_enricher connectors
```

### 5.1 Стенд на базе открытой SIEM (профиль `siem`)

Профиль `siem` поднимает открытую SIEM (OpenSearch, совместимый с Wazuh Indexer)
и демонстрирует полный цикл «индекс алертов → обогащение → индекс обогащённых событий»:

```bash
docker compose --profile siem up --build
```

Состав профиля:

| Сервис | Назначение |
|---|---|
| `opensearch` | открытая SIEM: хранилище алертов формата `wazuh-alerts-*` |
| `siem-demo` | засев индекса 120 событиями, запуск `siem-enricher run` с конфигурацией `config.opensearch.json`, проверка результата |

Проверка вручную:

```bash
# список индексов и пример обогащённого документа
docker compose exec siem-demo python /app/tools/seed_opensearch.py \
  --url http://opensearch:9200 --verify

# поиск в индексе обогащённых событий
curl -s "http://localhost:9200/siem-enriched-events-*/_search?size=1" | head -40
```

Конфигурация стенда: `config/config.opensearch.json` — источник `wazuh_indexer`
(индекс `wazuh-alerts-*`), приёмник `elasticsearch` (индекс `siem-enriched-events-%Y.%m.%d`).
Тот же сценарий без Docker выполняется инструментом `tools/seed_opensearch.py`
(только стандартная библиотека) и командой `python -m siem_enricher run --config config/config.opensearch.json`.

Проверка результата:

```bash
curl http://127.0.0.1:8080/healthz
curl http://127.0.0.1:8080/readyz
curl http://127.0.0.1:8080/metrics | head
cat var/enriched_events.jsonl        # файл из multi-приёмника
cat var/mock_siem_received.jsonl     # что приняла заглушка SIEM
```

Сборка без ML (меньше образ, только правила):
`docker build --build-arg INSTALL_ML=0 -t siem-enricher:lite .`

Веса модели в образ не копируются — каталог `ml/artifacts` монтируется томом
(`./ml/artifacts:/app/ml/artifacts:ro`).

## 6. Kubernetes

`deploy/k8s/siem-enricher.yaml` содержит: Namespace, ConfigMap, Secret, Deployment (2 реплики,
`startupProbe` на загрузку модели, liveness/readiness), Service, HPA (2–8 реплик по CPU),
NetworkPolicy (метрики — только из namespace `monitoring`).

Важно: при нескольких репликах хранилище происхождения должно быть сетевым —
`PROVENANCE_BACKEND=redis` (иначе цепочки будут расходиться по подам).

## 7. Наблюдаемость

Метрики Prometheus (эндпоинт `/metrics`, формат текстовый, реализация без внешних библиотек):

| Метрика | Тип | Смысл |
|---|---|---|
| `siem_enricher_events_consumed_total{source,status}` | counter | события, прочитанные из источника |
| `siem_enricher_events_enriched_total{status}` | counter | обогащённые события (ok/error) |
| `siem_enricher_enrichment_duration_seconds` | histogram | длительность обогащения события |
| `siem_enricher_sensitivity_classified_total{level,method}` | counter | классификации по классам и методам |
| `siem_enricher_ml_fallback_total{reason}` | counter | случаи отказа ML (нет артефакта/torch/категории) |
| `siem_enricher_risk_score` | histogram | распределение оценки риска |
| `siem_enricher_risk_severity_total{severity}` | counter | события по уровням риска |
| `siem_enricher_provenance_chain_depth` | histogram | глубина цепочек происхождения |
| `siem_enricher_policy_triggered_total{rule_id,decision,severity}` | counter | срабатывания правил |
| `siem_enricher_policy_actions_total{type,status}` | counter | выполненные действия |
| `siem_enricher_sink_sent_total{sink,status}` | counter | отправка в приёмники |
| `siem_enricher_source_errors_total{source}` | counter | ошибки чтения источника |
| `siem_enricher_uptime_seconds`, `siem_enricher_queue_size` | gauge | состояние сервиса |

Базовые алерты (пример): `rate(siem_enricher_events_enriched_total{status="error"}[5m]) > 0`,
отсутствие роста `events_consumed_total` при живом `/healthz`, рост `ml_fallback_total`.

## 8. Логи

* формат `json` (по умолчанию) — строки с полями `ts`, `level`, `logger`, `message`, `event_id`;
* формат `human` — для локальной отладки (`config.local.json`);
* уровень задаётся `SIEM_ENRICHER_LOG_LEVEL` или `--log-level`;
* в логах нет содержимого файлов и значений полей, подлежащих маскированию.

## 9. Диагностика

| Симптом | Причина | Решение |
|---|---|---|
| `readyz` возвращает 503 | не загружена модель/правила, недоступно хранилище | смотреть `/v1/version` (`pipeline`), логи, `validate-config` |
| События не приходят (`consumed_total` = 0) | неверный топик/группа, событий нет | `python tools/kafka_tool.py consume --topic siem.raw.events --from-beginning` |
| Всё уходит в правила (`ml_fallback_total` растёт) | нет torch/трансформеров или артефакта | `pip install -r requirements-ml.txt`, проверить `ml.artifact_path` |
| Цепочки пустые | TTL меньше возраста событий | передавать событие/`as_of` или увеличить `provenance.ttl_seconds` |
| Долгая загрузка контейнера | инициализация mBERT (~10–20 с на CPU) | `startupProbe` уже настроен; можно увеличить `start_period` |
| Kafka: смещения не коммитятся | не настроен `acks`/группа | проверить `group_id`, права на топик |

## 10. Производительность (измерено на CPU, mBERT)

| Режим | Задержка на событие | Пропускная способность (1 процесс) |
|---|---|---|
| Гибрид с ML (mBERT, ~2 объекта в событии) | ≈ 148 мс | ≈ 6.7 соб/с |
| Только правила (без torch) | ≈ 128 мс | ≈ 7.8 соб/с |

Основной вклад — инференс mBERT; задержка снижается увеличением `ml.batch_size`, переходом
на `cuda`, квантизацией модели или вынесением инференса в отдельный сервис.
